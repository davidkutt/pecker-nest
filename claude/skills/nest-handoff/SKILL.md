# Hand off a nest session

Fill in the field note for this session and give David the part he pastes into the planning chat. You report; you do not fix anything.

`<repo>` below is the repository's directory name (`basename "$PWD"`). The commands are the same in bash, zsh and fish.

1. **Find the field note.** It is the repository's open note, not today's newest: sessions run over several days. Run `node ~/dev/pecker-nest/scripts/field-note.ts open --repo <repo>`; it prints the newest note for this repository whose Session section has no end HEAD. If it prints nothing (exit code 1), create a note from `TEMPLATE.md`, say that the session was not supervised from the start, and fill in `Config under test` as `/nest-supervise` does (`node ~/dev/pecker-nest/scripts/field-note.ts config --repo <repo>`).
2. **Metrics.** Run `node ~/dev/pecker-nest/scripts/session-report.ts --cwd "$PWD" --since <date>`, where `<date>` is the note's start (for example `--since 2026-11-08T09:30`), so that every Pi session since supervision began counts and not only the last one. If `$ARGUMENTS` is given, use it instead (`--since <date>`, `--since 8h`, or a session file). Put the output under Metrics. It contains counts only, and it is offline. Run it once more with `--json` and keep the result at hand for the steps below.
3. **Outcome.** From the start HEAD in the note: `git log --oneline <start>..HEAD`, `git diff --stat <start>`, and untracked files from `git status --short`. Run the check command from `.pi/gate.json` (or the repository's documented check) and record the exit code and the last lines. Go through the task's acceptance checks one by one: met, not met or unknown, each with its evidence.
4. **Quality.** Read the diff from the start HEAD. Note concrete problems with `path:line`: bugs, weakened or skipped tests, scope creep, broken repository rules (`CLAUDE.md`, `AGENTS.md`). Do not fix them. Then fill in the table "Defects that passed the gate and the review": one row for every problem that is still in the final diff although nest's quality gate was green or handed back and its review (if one ran) did not report it. Sort each into exactly one kind:
   - `bug`: the code does the wrong thing, with the input or the case that shows it;
   - `weakened test`: a deleted, skipped or focused test, fewer test cases, an assertion that no longer checks anything, an added suppression (`@ts-ignore`, `# type: ignore`, `eslint-disable`, `# noqa`) or loosened lint, type or test configuration. Compare with the session report's line "Weakened-test check": a finding the gate reported and that is still there counts here too, and say whether the gate named it;
   - `rule break`: a rule of `AGENTS.md` or `CLAUDE.md` that the diff breaks, with the rule.
   Scope creep and style are not defects; they stay in the assessment. Write the total as three numbers, zeros included. Problems David or you fixed during the session are interventions, not defects that passed: count only what is in the final diff.
5. **Assessment.** What nest did well and badly, each with evidence (a file, a session-report number, a quality-gate round). Cover at least: did it plan before building, did DeepSeek V4.1 Flash cope or did the strong model have to step in and why, failed edits, loops, gate repair rounds, safety blocks that were right or wrong, cost. Three parts of the session report belong here:
   - Router, "Outcome of the switches": per reason and strong model, how many switches ended with a green gate, how many were handed back red, how many strong-model requests they took and what they cost. Say which strong model stepped in (GLM 5.3 by default, Kimi K3.1 Pro after `/strong kimi`) and write it into the note's `Strong model in the session` line.
   - Router, "Fallbacks at request time": a strong model that was ruled out and what took over.
   - "Providers": if request errors, failed tool calls or failed edits cluster on one upstream provider of a model, name the provider and the numbers. "–" means the provider was not recorded.
6. **Model comparison.** Only when the session ran one (RUNBOOK M5, "Modellvergleich GLM gegen Kimi"): fill in the field note's Model comparison table, one row per step — step, GLM result, Kimi result, cost of each, verdict. Take the costs from the session report per model (`stats.models`), not from an estimate; for a `/plan` comparison also compare `PLAN.glm.md` with `PLAN.md`. Judge each step on substance (did it find the real constraint, is the plan or review usable), not on length, and write a verdict per step plus one line overall. If no comparison ran, leave the table empty and say nothing about it.
7. **Interventions.** Check the table is complete; add a one-line total (count and estimated minutes). Count `admin` rows (pushing the branch, opening the PR) separately and leave them out of the total that measures nest: they are release work, not a repair of what nest built.
8. **Harness findings.** One row per finding: evidence, proposal, the bucket it belongs in (Do now, Validate, Validate & later, Don't) and the metric that would show it worked. Keep product issues out of this table; they go under Product notes.
9. **For the planning chat.** Write the last section, at most 40 lines: the configuration under test in one line (pecker-nest commit, and whether it differs from the previous note), outcome, key numbers (cost, requests per model, switches to the strong model and which one, failed-edit rate, gate repairs, interventions), the three most important findings, open questions. The key numbers always carry these two lines, also when they are zero or empty:
   - `Defects that passed gate and review: <n> bugs, <n> weakened tests, <n> rule breaks` from step 4. Interventions measure how much help nest needed; this line measures what it shipped.
   - `Escalation outcome:` followed by the session report's "Outcome of the switches" lines, unchanged, for example `gate, GLM 5.3: 3 switches, 2 green, 1 handed back; 14 strong-model requests, $0.42`; `none` when nothing escalated. Add the "Fallbacks at request time" lines if there are any.

   Had the session a model comparison, add its verdict in at most three lines (per step and overall), because the planning chat decides from it whether Kimi replaces GLM. Print exactly that section in your reply so David can paste it.
10. **Close the note.** Write the end HEAD (`git rev-parse --short HEAD`) after the arrow in `Start HEAD → end HEAD` and the end time in the line below. Only this closes the note: the next `/nest-supervise` in this repository then starts a new one. If David says the session goes on tomorrow, leave the end HEAD empty and say that the note stays open.

Rules: no secrets, no held-out eval samples, at most five-line code excerpts. The note stays local. Product status for the product's own planning chat belongs in its pull request description.
