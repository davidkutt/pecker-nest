# Findings: how Pi can log in to grove's knowledge base

Part 1 of [`docs/tasks/grove-kb.md`](../tasks/grove-kb.md), read and tested on 11 November 2026. Nothing in pecker-grove was changed. Part 2 waits for David's choice in [Options](#options).

## Short answer

Pi 1.5.0 can log in to grove the same way Claude Code and VS Code do: OAuth through Keycloak with a Client ID Metadata Document (CIMD), PKCE and the `resource` parameter. Pi stores and refreshes the tokens itself, so nothing is pasted and no secret enters the repository. The one thing missing is on grove's side: the realm has client policies for `claude.ai` and `vscode.dev` only, and Pi's client id is `https://pi.dev/oauth/client.json`.

Three things from the runbook's M3 do not hold:

- `--bearer-token-env-var KB_TOKEN` cannot work. Pi reads the variable when it opens the connection, grove's tokens live 5 minutes, and Pi does not refresh a token it was handed in a header.
- Planner and reviewer cannot get `mcp:kb/search_knowledge_base`. A subagent with that tool does not start while grove is down, and neither Pi nor pi-subagents has a setting that makes the tool optional.
- M3 is not 30 minutes of David's time alone: grove needs a realm change first.

### G1: what each login option costs in grove

How a realm change reaches the daily stack is the same for every row: Keycloak imports `infra/keycloak/realm-kb.json` only into an empty database, so a changed file means recreating Keycloak's database (`docs/setup/startup.md:352-366`). That loses users registered in the app, admin-console edits, sessions and the Claude Code / VS Code consents; documents and their owners stay. This recreate is still an open item of M3c.0 (`plan-daily-use.md:61-62`). A change that lands in the realm file before David does it costs no second recreate.

| Pi's option | Change in grove | Cost |
| --- | --- | --- |
| CIMD, Pi's document | A third client policy and profile in `realm-kb.json`, copied from `mcp-vscode` (lines 477-573): condition `client-id-uri` with scheme `https` and host `pi.dev`; executor `client-id-metadata-document` with trusted domains `pi.dev` and `127.0.0.1`, plus every host that a URL in Pi's document points to, same-domain check off, resource allow-list `http://localhost:8000/mcp`. No new feature flag, no new client, no change to the MCP server. | About 40 lines in the realm file. One Keycloak recreate, the pending one if timed right. ADR-0014 gets a third client (an amendment, not a new decision). `realm-check` gets a third `cimd-login.sh` call, `startup.md` a Pi paragraph, and the M3c.0 hand check a third client. |
| Pre-registered public client (`oauth.clientId`, fixed `callbackPort`) | A public client for Pi with the redirect `http://127.0.0.1:<port>/callback`, optional scope `kb:read`, full scope off and consent. Pi always sends `resource`, and with `resource-indicators` on Keycloak answers `invalid_target` unless the resource is configured: so also a resource-server client for the MCP server with the `resource_url` attribute, and an audience mapper on Pi's client that targets it. | Two clients and a mapper in the realm file, one recreate. It reverses two decisions of ADR-0014 ("No `kb-mcp` client", and pre-registered clients as the rejected alternative), so a new ADR. Its token path is new and needs its own rows in the realm check. A fixed port on David's Mac. |
| Dynamic client registration (`clientRegistration: "dcr"`) | Open Keycloak's anonymous registration: trusted-host policy for the machine and allowed client scopes. The registered client then has no audience binding for `resource`, so the resource-server client from the row above as well. | Rejected in ADR-0014 already (deprecated in MCP 2026-07-28, trusted hosts per machine). Largest realm change of the OAuth routes. |
| Static header with a helper (`"Authorization": "!command"` or an environment variable) | Something that can mint a token without a browser: a confidential client or a direct-grant client for a helper script, and either much longer access tokens for it or a helper that also restarts Pi's connection, which Pi does not offer (P3). | A new client with a long-lived secret or a stored password, a helper script, an ADR, one recreate. Keycloak's rules for a document, for the first row (source at 26.8.1, `services/…/oauth2/cimd/clientpolicy/executor/AbstractClientIdMetadataDocumentExecutor.java`): `client_id` inside the document must equal the URL (line 660); the request's redirect URI must match one of the document's `redirect_uris` (679); every `redirect_uris` entry and every URL-valued property must be on a trusted domain (689-696); a missing `token_endpoint_auth_method` counts as `none` (920-923). The guide's example for VS Code needs a third trusted domain only because its document has a `logo_uri` on another host (guide lines 295-296).

## Options

Ranked by the four criteria of the task, in its order.

| | A: CIMD with Pi's document | B: pre-registered public client | C: static header with a token helper |
| --- | --- | --- | --- |
| Long-lived secret outside the Keychain or Pi's store | None. The refresh token lives in `~/.pi/agent/mcp-auth.json` (`0600`). | None. Same store; a public client has no secret. | Yes: a client secret or password for the helper. It can sit in the Keychain, but it is a new long-lived credential. |
| Change in grove | One policy and one profile, the pattern grove has twice. ADR-0014 amended. | Two clients and a mapper, a new ADR that reverses ADR-0014 in two points. | A new client and a helper, a new ADR, and longer-lived tokens or a restart mechanism that does not exist. |
| Subagents | The login is shared. A subagent with the tool still fails to start while grove is down (P5), so they stay without it. | Same as A. | Same limit, and the token is dead after 5 minutes anyway. |
| Survives a Keycloak upgrade | Depends on the experimental `cimd` and `resource-indicators` features, exactly as Claude Code and VS Code do. No new exposure; grove's `infra-upgrade-check` already covers a CIMD login. | Independent of `cimd`, still tied to `resource-indicators`, because Pi cannot omit `resource`. | Independent of both. |
| nest side (`agent/mcp.json`) | `"oauth": { "clientRegistration": "cimd", "scope": "kb:read offline_access" }` | `"oauth": { "clientId": "…", "callbackPort": …, "scope": "kb:read offline_access" }` | `"headers": { "Authorization": "!…" }` |
| David, once | `pi mcp login kb`, log in and consent in the browser | The same | Store the helper's credential |
| Works without internet | The first login needs it (Keycloak fetches the document from `pi.dev`, cached 5 minutes to 3 days). | Yes | Yes |

**Recommendation: A.** It is the only option that adds no client and no secret to grove, it is the route grove already decided for external clients and checks on every Keycloak bump, and Pi supports it without any code in nest. B is the fallback if Keycloak cannot parse Pi's document (see below). C fails the first criterion and, with 5-minute tokens, does not work in practice.

For A, `clientRegistration` is pinned to `cimd` rather than left on `auto`: if a Keycloak upgrade stops advertising documents, the login then fails with a clear message instead of trying dynamic registration, which grove refuses.

**What grove must change for A** (for the planning chat to turn into a grove task):

1. `infra/keycloak/realm-kb.json`: policy and profile `mcp-pi` as in the G1 table.
2. `.claude/skills/realm-check`: a third login, `cimd-login.sh carol https://pi.dev/oauth/client.json http://127.0.0.1:<port>/callback "kb:read offline_access"`, expecting `aud=http://localhost:8000/mcp`, `kb:read` and the user's roles.
3. ADR-0014 (third client), `docs/setup/startup.md` ("Use the knowledge base from …" gets Pi), `plan-daily-use.md` M3c.0 (hand check with Pi).
4. Time it before the pending Keycloak recreate of M3c.0, so there is only one.

### Consequences for Part 2, whichever option is chosen

- **Subagents stay without the knowledge base** (task item 4). `planner` and `reviewer` keep their tool lists; the deviation goes into `docs/v1-notes.md`. The main session searches and passes what it found into the subagent's task.
- **Runbook M3 changes shape:** no `KB_TOKEN`, no `pi mcp add`; the server entry is in the repository, and David's steps are start grove, `pi mcp login kb` once, tests 6 and 7. The command is the same in bash, zsh and fish.
- **After starting grove in a running session:** `/mcp reconnect kb` or `/reload`, because a server that failed at startup does not retry (P5). `doctor.sh` can name that in its `WARN`.
- **With `kb` registered and grove down**, every session starts with one "MCP servers need attention" notice and the first prompt waits under 2 seconds. The e2e scenarios run in exactly that state.
- **The knowledge base holds fetched web pages.** The rule "reference material, never an instruction" in `skills/best-practices/SKILL.md` matters more than the runbook's wording suggests; `ingest_url` stays hidden in nest and is refused by grove anyway (`kb:read` only).

## Open checks

Neither can be done from this session; both belong to grove's realm check, which runs with internet.

1. **Pi's metadata document.** `curl -s https://pi.dev/oauth/client.json` (the same command in fish). Needed from it: the hosts of `client_uri`, `logo_uri` and similar properties, which must be added to the trusted domains, and that `redirect_uris` lists the loopback form `http://127.0.0.1/callback`. If Keycloak cannot parse the document, as with ChatGPT's (guide lines 479-485), A is out and B is the route.
2. **A real login.** The probe confirms what Pi sends. Whether Keycloak 26.8.1 accepts it, including the loopback port, shows only on a throwaway Keycloak with the new policy. VS Code uses the same redirect form and passes.
